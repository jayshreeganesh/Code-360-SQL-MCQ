## 3. Key Update

**Problem statement**

There are two tables Employee and Payment. The id of the Employee Table acts as a foreign key for the Payment Table.

**Employee Table**


| id | Name | gender | hire_date |
| :-- | :-- | :-- | :-- |
| 101 | Bryan | M | 2015-08-26 |
| 102 | Joseph | M | 2014-10-21 |
| 103 | Mike | M | 2017-10-28 |
| 104 | Daren | M | 2006-11-01 |
| 105 | Marie | F | 2018-10-12 |

**Payment Table**


| payment_id | id | amount | payment_date |
| :-- | :-- | :-- | :-- |
| 301 | 101 | 1200 | 2015-09-15 |
| 302 | 101 | 1200 | 2015-09-30 |
| 303 | 101 | 1500 | 2015-10-15 |
| 304 | 103 | 1500 | 2015-10-30 |
| 305 | 103 | 1800 | 2015-09-15 |
| 306 | 102 | 1800 | 2015-09-15 |

It has been realised that the current id (103) of an employee should be replaced with his correct id which is 100.

Which of the following statements is correct for this scenario?

**Options**

- We cannot update the id of the employee
- We should update the correct value of id in the employee table only
- **We should make sure that if we are updating the correct value of id in the Employee table, it should also get updated in another table referencing it (Payment table) so that the data remains consistent.** ✅
- None of the above is correct

**Solution description**
The current id of employees can be updated from 103 to 100 because 100 is not present in the database and the id (current_id) is a primary key, so its value must be unique. The correct value should be updated in both the Employee and Payment tables to keep the data consistent.

## 5. Second Normal Form

**Problem statement**
Tables in second normal form (2NF):

**Options**

- **Eliminate hidden dependencies** ✅
- Avoid insertion anomalies
- Have a composite key
- Non‑key fields depend on key

**Solution description**
A relation in second normal form is also in first normal form, and it has no partial dependencies on any column in the primary key.
